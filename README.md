# Анализ веб-приложения и клиент-серверного взаимодействия

## 1. Исследуемая информационная система

Для выполнения лабораторной работы используются информационная система Ozon и пользовательский сценарий: поиск товара и добавление в корзину.

Ozon — онлайн-площадка, предназначенная для покупки и продажи товаров и отслеживания их местоположения (интернет-магазин). Сервис не требует написания программного кода, пользователь работает через веб-интерфейс, который формирует запросы к серверу, а сервер возвращает данные и обновляет состояние страницы.

В ходе лабораторной работы были выделены следующие основные компоненты:
- браузер пользователя;
- интерфейс сайта (frontend);
- клиентский JavaScript, управляющий редактированием страницы;
- сервисный API, принимающий запросы от клиента;
- backend, обрабатывающий данные;
- хранилище данных для сохранения информации о товарах, их нахождения в корзине пользователя;
- внешние ресурсы и сервисы.

## 3. Анализ HTTP-ответов

После отправки запроса сервер возвращает HTTP-ответ, содержащий статус-код, заголовки и тело ответа. Для анализа был выбран следующий запрос: добавление товара в корзину. Был получен ответ с кодом статуса 200, что свидетельствует об успешном выполнении операции, после чего браузер изменил интерфейс и отправил результат в формате JSON.

![Заголовки HTTPS-ответов](/images/screenshots/INF-Part2-step3-1.png)

Основные наблюдаемые заголовки:
- Content Type: application/json;
- Data: дата и время ответа;
- Server: название серверного программного обеспечения.

Пример структуры ответа, обнаруженный в разделе **Ответ** вкладки **Сеть**:

```json
{
    "trackingInfo": null,
    "trackingPayloads": {},
    "trackingTokenAliases": null,
    "data": {
        "success": true,
        "cart": {
            "cartItems": [
                {
                    "id": 250051692,
                    "qty": 1
                }
            ]
        }
    }
}
```

При изучении ответа были найдены данные об идентификаторе выбранного товара и его количестве. Браузер получал эти данные и изменял интерфейс при добавлении товара в корзину.

![Идентификатор и количество товара в DevTools](images/screenshots/INF-Part2-step3-2.png)

Наблюдаемые факты: после добавления товара в корзину сервер возвращает JSON-ответ, а в DevTools появляется HTTP-запрос с методом POST, который задаёт интерфейс корзины пользователя.

Предположения: запрос передаётся от frontend через API в backend, который изменяет внешний вид страницы и возвращает новую версию клиенту.

## 4. Анализ параметров и передаваемых данных

При выполнении пользовательского сценария браузер передаёт серверу информацию, которая позволяет понять, какое действие нужно выполнить. При добавлении товара в корзину передаются следующие параметры:
1. Команда действия (addToCart).
2. Идентификатор товара.
3. Количество товара.
4. Дата и время операции.
5. Тип передаваемых данных.
6. Версия и кодировка браузера.

Часть параметров была найдена в теле HTTP-запроса (полезная нагрузка, пункты 1-3), а другая в заголовках (пункты 4-6). После выполнения операции сервер возвращает результат и изменённый вид витрины товара, чтобы пользователь видел изменённое состояние без перезагрузки страницы.

## 6. Взаимодействие Frontend, API и Backend

При выполнении пользовательского сценария важным аспектом является понимание цепочки событий от действия пользователя до визуального обновления интерфейса.

Последовательность событий при добавлении товара в корзину можно описать следующим образом:
- интерфейс витрины товара;
- клиентский frontend в JavaScript;
- HTTP-запрос к API;
- серверный backend;
- обработка и сохранение данных;
- HTTP-ответ от API;
- обновление интерфейса витрины товара.

Более детальное описание процесса действия выглядит так:
1. Пользователь взаимодействует с элементом веб-интерфейса.
2. Frontend реагирует на действие пользователя и формирует запрос.
3. Браузер отправляет запрос на API (HTTP-метод POST).
4. API принимает запрос и передаёт его backend.
5. Backend обрабатывает данные (количество и идентификатор товара) и сохраняет их в структуре страницы.
6. Сервер отправляет ответ на API со статусом успешного выполнения.
7. API принимает ответ и передаёт его frontend.
8. Frontend обновляет визуальную структуру страницы — изменяет вид витрины товара.
9. Пользователь видит, что выбранный товар был добавлен в корзину.

В результате было подтверждено, что клиент и сервер взаимодействуют через HTTP, браузер не хранит состояние страницы в одном файле, а передаёт и получает данные при помощи API, благодаря чему приложение не требует перезагрузки страницы для отображения изменений в интерфейсе.

## 7. Сопоставление с архитектурой из лабораторной работы №1

По результатам предыдущей лабораторной работы была сделана архитектурная схема информационной системы. В этой лабораторной работе она была сопоставлена с сетевым поведением приложения.

В частности, были подтверждены следующие элементы архитектуры:
- с браузера начинается взаимодействие пользователя с системой;
- frontend загружает интерфейс, обрабатывает действия пользователя и формирует HTTP-запросы;
- API выступает посредником в обмене данных между клиентом и сервером;
- backend обрабатывает запросы и обновляет состояние страницы;
- данные сохраняются не только в памяти браузера, но и в хранилище данных;
- cookies используются для поддержания пользовательской сессии.

Однако некоторые элементы архитектуры требуют доступа к серверной части и не отображаются в DevTools, поэтому они остаются предположениями:
- язык программирования backend;
- база данных на сервере;
- что обрабатывается во внешних сервисах.

По результатам исследования стало известно, что взаимодействие с системой идёт с участием следующих элементов:
- пользователь;
